The problem it solves

Every release meant a person opening the portal and clicking through the same journeys: sign up, log in, find a course, finish it, take the quiz, collect the certificate — then repeating that for each role, in two languages, on three environments. It took hours, it was tested the same way twice only by luck, and anything slow or subtly broken slipped through simply because nobody had time to check it again.

What a learner does, the automation now does

The suite drives a real browser through the real portal — no mocks, no shortcuts.

Sign up→ Read the OTP from the inbox→ Accept T&C→ Browse courses→ Watch videos & read PDFs→ Answer the quiz→ Climb competency levels→ Download the certificate ✓

It signs up a brand-new learner each run, because a fixed account has already finished the course after the first run and would prove nothing. The OTP is read from the real inbox, and the quiz is answered from the portal's own answer key — so a pass means the journey genuinely worked, not that a check was skipped.

How it was built, in four stages

1 · Make one journey work by hand

Start with the single most valuable path — sign up and finish a course — and get it passing reliably once. Everything else is a variation of that.

2 · Make it survive the real portal

The hard part was never writing clicks; it was the portal's own behaviour. The suite had to learn that pages render in Hindi as readily as English, that a quiz submits one question at a time, that a signup address longer than 19 characters is silently rejected, and that a logged-out session still looks logged in from the outside. Each of those was a real failure, found once and then handled for good.

3 · Make the results readable

A pass/fail list helps nobody outside the team. Every run now produces a branded HTML report with screenshots, an Excel sheet, and a PDF to attach to an email — plus the downloaded certificates as evidence.

4 · Make it run without me

The suites moved into GitHub, where they start themselves: on a schedule, on every release, and — once the deploy pipeline sends one signal — within seconds of a new build reaching an environment.

Things it has actually caught

  • A course stuck at 86% — every module consumed, yet the portal never recorded completion, because the final assessment submitted after a single question.
  • A badge that appears on production and not on staging for the same learner — invisible from the course side, where everything looked finished.
  • Certificates listing 1 of N when a learner had earned several.
  • Pages that render only in Hindi on some orgs, where English-only checks quietly passed over them.
  • A login that failed without saying so — the portal accepted bad credentials and returned an anonymous session, which made tests fail twenty steps later for reasons that had nothing to do with login.

How the spec files were actually written

Record the journey first, then turn that recording into something that can run unattended a hundred times.

Step 1 · Record the journey by doing it

Playwright ships a recorder. You point it at the portal and click through as a learner would, and it writes the code for every click and keystroke as you go.

# opens the portal, plus a window that writes code as you click
npx playwright codegen https://portal-staging.aastrika.org

Five minutes of clicking gives a working first draft — and, more valuable, it shows what the portal really does, including steps nobody wrote down.

A real example of why recording first matters

An in-course quiz kept failing: the run answered question one and stopped. A recording of a person taking that quiz showed the actual rhythm — pick an option → Submit → Next, repeated for every question. That "Submit" belonged to the question, not the quiz, and the automation had been reading the first one as "finished". Nothing on screen says this; the recording showed it in seconds.

Step 2 · Turn the recording into a test

A raw recording is a starting point, never the finished article. It captures one run: that day's data, that session's ids, no checks, and no patience for a slow page. The clean-up is the real work.

What the recorder writes

click('#mat-radio-94')
goto('…/auth?tab_id=xY9')
fill('#otp', '483921')
click('text=Submit')

What it has to become

chooseOption(correctAnswer)    // from the key
followRedirect()               // ids expire
fill(await readOtpFromInbox()) // live
clickQuizSubmit()              // not the player's

Step 3 · Watch it, then stop watching it

A new spec runs with the browser visible until it passes twice in a row, then runs hidden. Anything repeated across specs — logging in, reading an OTP, finding a button in either language — moves into a shared helper, so it is written once and fixed once.

# watch it work
npx playwright test tests/create-account.spec.ts --project=Chrome --headed

# slow it down enough to follow by eye
$env:SLOW_MO="250"

Giving the demo

Ten minutes, in this order. The live run does the convincing; everything else is commentary.

0–1 min
Set up

Open the portal and say what one release used to cost: every journey, every role, two languages, three environments — all by hand. That is the number everything else is measured against.

1–4 min
Run it live

Start a signup with the browser visible. Let people watch it fill the form, fetch the real OTP from the inbox, and land on the signed-in home. This is the moment the room understands it.

cd D:\Automation\SphereWebAutomation
$env:BASE_URL="https://portal-staging.aastrika.org"; $env:SLOW_MO="250"
npx playwright test tests/create-account.spec.ts --project=Chrome --headed
4–6 min
While it runs

Open a report from an earlier run — screenshots, timings, the downloaded certificate. Say that this is what gets attached to the release email, and that nobody assembles it by hand.

6–8 min
It runs itself

Open GitHub → Actions. Show a run nobody started: one from the schedule, one triggered by a deployment. Open its artifacts to show the same report produced in the cloud.

8–10 min
What it caught

Finish with one real defect — the course stuck at 86% with every module finished, or the badge that showed on production and not on staging. A found bug persuades people more than any pass rate.

Before you present

  • Rehearse once on the same machine and network — signup depends on a live inbox.
  • Keep a finished report open in a tab, in case the portal is slow on the day.
  • Run npm run check:login first: twenty seconds, and it tells you the demo will get in.
  • Have the account details to hand — a demo that stops to debug a password loses the room.
